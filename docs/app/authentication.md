# Add sign-in and maintain a session

> Sign in through a hosted page, verify the account on your API, and restore or end the app session safely.

Start with one result: **Sign in** opens a browser, completing sign-in returns
to the app, and the screen changes to **Signed in** only after your API accepts
the session. Closing the browser leaves the app signed out.

This walkthrough uses Auth0 as a concrete hosted backend for iOS and Android.
It supplies the actual authorization, exchange, refresh and revocation endpoints;
Xplat supplies the native ceremony and credential lifecycle. You need a running
[phone starter](../start/toolchain.md#run-on-ios-and-android), an Auth0 tenant and
Node.js on your development computer. Browser and experimental desktop choices
are explained [below](#choose-another-target-or-sign-in-method).

## Register the app and API

An **access token** lets an app call your API for a limited time. A **refresh
token** obtains another access token after it expires. The app uses a public
client ID; a client secret must never be bundled into a phone app.

In the Auth0 Dashboard:

1. Create an application of type **Native**. Copy its **Domain** and **Client ID**.
2. Add `com.example.packing://auth/callback` to **Allowed Callback URLs**. Replace
   the example scheme with an app-specific value you control, and use that exact
   callback in the app configuration below.
3. Enable **Authorization Code** and **Refresh Token** grants, with token endpoint
   authentication method **None** for this public client.
4. Register a custom API with an identifier such as `https://packing-api.example`,
   select RS256 signing, allow this application to access it, and enable **Allow
   Offline Access**. The identifier is the token's intended audience; it can
   differ from the development server's address.
5. Enable a login connection for the application and create a test user. Start
   with the tenant's database connection; add Google or Apple after this path works.

These settings follow Auth0's [public-client PKCE workflow](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow-with-pkce/call-your-api-using-the-authorization-code-flow-with-pkce).
**PKCE** binds the returned one-use code to a secret generated by this app
attempt. The secret stays out of the browser URL. Keep provider settings and
app identifiers separate from user credentials.

Write down these values before proceeding:

| Value | Example | Used by |
| --- | --- | --- |
| Issuer | `https://YOUR_TENANT.auth0.com/` | App adapter and API verifier |
| Native client ID | Your public Native application's ID | App adapter |
| Audience | `https://packing-api.example` | Authorization request and API verifier |
| Callback | `com.example.packing://auth/callback` | Auth0 allowlist and native callback registration |
| API origin during development | `http://127.0.0.1:8788` | App's authenticated requests |

## Start an API that verifies the token

Use the small maintained [guide API](../../tools/auth-guide/README.md) for the
first check. It verifies signatures using the configured issuer's public keys,
checks issuer, audience, expiry and subject, then returns only the authenticated
subject from `GET /api/me`. It does not accept a user ID supplied by the app.
The handler is a Fetch-style function, which the supplied Node server calls:

```ts
import { createApi } from './api.ts'

const handle = createApi({
  issuer: 'https://YOUR_TENANT.auth0.com/',
  audience: 'https://packing-api.example',
})
const response = await handle(new Request('http://127.0.0.1:8788/api/me'))
console.log(response.status) // 401; no token supplied
```

Auth0's [access-token validation requirements](https://auth0.com/docs/secure/tokens/access-tokens/validate-access-tokens)
explain why decoding token text alone is insufficient.

In a separate directory from your app, create the API project:

```sh
mkdir packing-api
cd packing-api
pnpm init
pnpm add jose@6
```

Copy [api.ts](../../tools/auth-guide/src/api.ts) and
[serve.ts](../../tools/auth-guide/src/serve.ts) into this project's `src/`
directory. Use Node.js 22.22.2 or newer, and set `"type": "module"` in its
`package.json`. Create `.env` in the API directory with your issuer and audience:

```dotenv
AUTH_ISSUER=https://YOUR_TENANT.auth0.com/
AUTH_AUDIENCE=https://packing-api.example
```

Replace the tenant value and use the audience registered above. Start the API:

```sh
node --env-file=.env src/serve.ts
```

Expect `Guide API listening on 127.0.0.1:8788`. In another terminal, request the
account without signing in:

```sh
curl -i http://127.0.0.1:8788/api/me
```

Expect **401**. This confirms the server is reachable and refuses an anonymous
request. The verifier uses `jose`, a maintained JWT library, rather than a
handwritten signature check. Here is the endpoint's full response contract:

| Request or condition | Status | Body |
| --- | --- | --- |
| Missing credentials | 401 | Empty |
| Invalid or expired access token | 401, with `WWW-Authenticate: Bearer error="invalid_token"` | Empty |
| Verified token | 200 | `{"subject":"provider-account-id"}` |
| Provider keys temporarily unavailable | 503 | Empty; retry later |
| Other path or method | 404 or 405 | Empty |

The sample implements one identity endpoint. In your real API, authorize each
resource operation using the verified identity and its permissions. Deployment,
HTTPS, rate limits and business-data access belong to that API. Never use the
Auth0 Management API identifier as the audience for this example.

## Connect the native callback

Install the app dependencies from your Xplat app directory:

```sh
pnpm add @octane-xplat/auth @octane-xplat/platform
```

The auth package brings its secure-storage implementation. Add this filter
inside the existing main activity in
`App_Resources/Android/src/main/AndroidManifest.xml`. Keep its `singleTask`
launch mode, and substitute the callback scheme chosen above:

```xml
<intent-filter>
  <action android:name="android.intent.action.VIEW" />
  <category android:name="android.intent.category.DEFAULT" />
  <category android:name="android.intent.category.BROWSABLE" />
  <data android:scheme="com.example.packing" android:host="auth" android:path="/callback" />
</intent-filter>
```

The active iOS system-authentication session captures the callback scheme;
this Xplat hosted ceremony does not need an additional iOS URL-type entry.
That differs from general [incoming links](navigation.md#handle-incoming-links)
and native provider SDK setup. Rebuild the native app after manifest changes.

For local Android emulator/device development, reverse the API port so the app
can use the same loopback URL as the computer:

```sh
adb reverse tcp:8788 tcp:8788
```

Select the intended device with `adb -s DEVICE_SERIAL reverse ...` if several
are connected. An iOS simulator can use the computer's loopback address. A
physical iPhone needs an HTTPS deployment reachable from the phone; replace
`apiOrigin` accordingly. The starter's iOS `Info.plist` allows local networking
for development; preserve that setting for the loopback test. The hosted Auth0
page always uses HTTPS.

If Android blocks the local HTTP request, create
`App_Resources/Android/src/main/res/xml/network_security_config.xml` with a
loopback exception for development, retaining other app-specific configuration:

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
  <base-config cleartextTrafficPermitted="false" />
  <domain-config cleartextTrafficPermitted="true">
    <domain>127.0.0.1</domain>
  </domain-config>
</network-security-config>
```

The starter manifest already references that resource. Keep production API
traffic on HTTPS; this exception is for the local test server.

## Add the client and account screen

Create `src/auth/` in your app and copy these maintained example files into it:

| Source | App filename | Responsibility |
| --- | --- | --- |
| [Auth0 flow](../../packages/auth/examples/auth0-flow.ts) | `auth0-flow.ts` | Exact provider endpoints, callback validation, refresh and revocation |
| [Account session](../../packages/demos/src/auth-guide/session.ts) | `session.ts` | Observable account state and handling late results or failed sign-out |
| [Account screen](../../packages/demos/src/auth-guide/AccountScreen.tsx) | `AccountScreen.tsx` | Sign-in, retry and sign-out controls subscribed to that state |

Keep those relative filenames. They are application examples to copy and adapt,
not imports from the framework's demo package. Add `src/auth/client.ts` below,
replacing the issuer and client ID with your registered values. Instantiate
this owner once, outside component rendering:

```ts
import { createHostedAuth } from '@octane-xplat/auth'
import { createAuth0Flow } from './auth0-flow'
import { createAccountSession } from './session'

export const auth = createHostedAuth({
  apiOrigin: 'http://127.0.0.1:8788',
  storageKey: 'packing-auth',
  flow: createAuth0Flow({
    issuer: 'https://YOUR_TENANT.auth0.com/',
    clientId: 'YOUR_NATIVE_CLIENT_ID',
    audience: 'https://packing-api.example',
    redirectUri: 'com.example.packing://auth/callback',
  }),
})
export const account = createAccountSession(auth)
```

Keep the copied adapter app-owned. Its provider endpoints and validation are
part of your integration; they are not additional framework exports.

Render the screen from your existing home route. For example, replace the
home component in `src/app/index.tsrx`, preserving any app-owned setup around it:

```tsrx
import { AccountScreen } from '../auth/AccountScreen'
import { account } from '../auth/client'

export default function Home() @{
  <AccountScreen account={account} />
}
```

Run the phone app. Expect **Signed out**, then press **Sign in**. Complete the
hosted test-user login. The callback should close the system browser, the app
should call `/api/me`, and the screen should say **Signed in**. If you close the
browser first, expect **Sign-in cancelled** and a retryable Sign in action.
Do not print callback URLs, codes, tokens, or provider exception text while testing.

## Restore, refresh and sign out

The maintained account screen invokes `restore` at startup. If you replace that
screen, call restoration from your own startup owner. Stored credentials are
only a starting point: the controller checks `/api/me` before publishing an
authenticated account:

```ts
import { account } from './client'

export async function restoreAccountAtStartup() {
  await account.restore()
}
```

Other screens subscribe with `useStore` so they receive updates on native as
well as web:

```tsx
import { Text } from '@octane-xplat/ui'
import { useStore } from '@octane-xplat/ui/data'
import { account } from './client'

export function AccountStatus() {
  const state = useStore(account.state)
  return <Text>{state.status === 'authenticated' ? 'Signed in' : 'Account unavailable'}</Text>
}
```

Use the auth client's transport for protected API requests. Its default policy
attaches the access token to same-origin `/api/*` paths, excluding `/api/auth`.
It refreshes an expired token before use and retries once after a Bearer
`invalid_token` challenge in the same session:

```ts
import { auth } from './client'

export async function checkCurrentAccount() {
  const response = await auth.fetch('/api/me')
  if (!response.ok) throw new Error('Account check failed')
  return response.json()
}
```

The Auth0 adapter refreshes through `/oauth/token`. A revoked refresh credential
clears the session; a temporary service failure leaves credentials available
for a retry. Auth0 can rotate refresh tokens, so retain the newly
returned token. The maintained adapter also handles a response that keeps the
previous refresh token. Keep the refresh token in secure storage, never ordinary
settings or logged output.

Press **Sign out** to retire the app's account and pending results immediately,
then remove saved credentials and attempt provider revocation. The controller
also supports calling the same action from an app command:

```ts
import { account } from './client'

export async function endAppSession() {
  await account.signOut()
}
```

If credential deletion fails, the screen stays without private content and shows
**Retry sign-out**. Retry that action; do not claim durable removal or restart
restoration until it succeeds. Credential saving and remote revocation are
best-effort in the current framework. Check restoration after restarting the
app as part of release qualification.

Ending the app session does not erase a provider's browser SSO session or
instantly invalidate already-issued access tokens on every API. Auth0 documents
[refresh-token revocation](https://auth0.com/docs/secure/tokens/refresh-tokens/revoke-refresh-tokens).
If your product requires provider-wide logout or immediate server revocation,
implement that policy on the provider/API as well.

## Retire protected routes when the account changes

The account controller changes an `authority` number whenever account ownership
changes. Subscribe at the root outlet to retire retained private screens and
pending route work together:

```tsx
import { RouteOutlet, Text } from '@octane-xplat/ui'
import { useStore } from '@octane-xplat/ui/data'
import { account } from './auth/client'

export function SessionRoutes() {
  const state = useStore(account.state)
  return <RouteOutlet authority={state.authority}>
    <Text>Choose a screen.</Text>
  </RouteOutlet>
}
```

Keep the session owner and shared providers outside this replaceable outlet.
Routing context and guards must read the current account, and the API must still
check every protected request. Follow [return after sign-in](navigation.md#return-after-sign-in)
for guards, validated return URLs, and the `resumeUrl` handoff when a successful
login also replaces the outlet owner. Router retirement does not clear an
application's separate query clients or stores; dispose account-owned data when
replacing that account.

## Offer Google or Apple on the hosted page

First verify the test-user path above. For Google, configure the hosted connection:

1. Create/select a Google Cloud project, configure its OAuth branding/audience,
   and add test users while the application is in testing.
2. Create a **Web application** OAuth client. Register the Auth0 domain as an
   authorized origin and `https://YOUR_AUTH0_DOMAIN/login/callback` as its redirect.
3. Put that Google client ID and secret into Auth0's Google social connection,
   enable the connection for your Native application, and save.
4. Repeat the app sign-in and choose Google on the hosted page. Check the returned
   account through `/api/me`, not the Google button's appearance.

Follow the [current Google connection steps](https://auth0.com/docs/authenticate/identity-providers/social-identity-providers/google).
The Google secret belongs in provider configuration, not the app bundle.

For Apple's hosted connection:

1. Enable Sign in with Apple on the primary Apple App ID. Create a Services ID
   associated with it and register the Auth0 domain and HTTPS return URL.
2. Create the Sign in with Apple key and record its key ID and your team ID.
3. Configure Auth0's Apple connection with the **Services ID**, team/key IDs and
   signing key; enable it for the application.
4. Complete Apple sign-in on the hosted page and repeat the account check.

Use Apple's [web configuration](https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web)
and [key creation](https://developer.apple.com/help/account/capabilities/create-a-sign-in-with-apple-private-key/)
instructions. Auth0's [redirect troubleshooting](https://support.auth0.com/center/s/article/Sign-in-with-Apple-invalid-redirect-url)
explains the Services ID and `/login/callback` requirement. Keep the private key
on the provider/backend side. Native Apple SDK entitlements are a different
integration from this hosted page.

## Choose another target or sign-in method

| Need | Use |
| --- | --- |
| Native hosted login with another backend | Supply its real `HostedAuthFlow` exchange, refresh and revocation contract; the framework transport stays the same |
| Browser app | Use your backend's browser cookie flow or the provider's browser SDK in a `.web.ts` implementation |
| Native Apple/Google SDK buttons | Follow [provider SDK setup](../platform/platform-services.md#provider-sdk-sign-in-apple--google) and verify the provider credential on the backend before issuing your app session |
| Browser passkeys | Use [WebAuthn and a relying party](../platform/platform-services.md#passkeys-and-auth-ceremonies) that verifies the stored challenge, origin and credential |
| Experimental AppKit app | Use the same hosted client when its capabilities are available; follow [native host and secure-storage setup](../platform/macos-native.md) |

Check availability before offering the native ceremony; it reports unsupported
on web:

```ts
import { auth } from './client'

const canOfferNativeSignIn = auth.supported
```

Keep DOM-based browser SDK code in a platform file and choose an implementation
with the same app-owned session interface. Auth0's [browser quickstart](https://auth0.com/docs/quickstart/spa/vanillajs)
covers its registered SPA client, browser origins, callbacks and SDK session
lifecycle. Never put a native refresh credential into browser local storage to
make the native client appear supported.

## Recover when the first sign-in fails

| Symptom | Check |
| --- | --- |
| Browser reports an invalid callback | Match the exact callback in Auth0, the adapter and the Android filter; rebuild after manifest changes |
| Browser returns, but account check fails | Match issuer and audience on both sides; confirm API access and Offline Access for the Native client |
| API is unreachable on Android | Run `adb reverse`, check the loopback cleartext configuration, and keep the API terminal running |
| It works on the simulator but not a physical iPhone | Use an HTTPS API address reachable from that phone |
| Sign-in works until restart | Check secure-storage availability in the distributed app; saving is best-effort |
| API returns 503 | Restore connectivity or provider-key access, then use Retry account check; do not erase credentials solely for this outage |

## Verify the complete flow

On each configured native target:

1. Complete login and confirm `/api/me` succeeds before private content appears.
2. Restart the app. Confirm account verification runs again and the saved session
   restores. Revoke the test session and confirm it cannot silently restore.
3. Cancel login and try again. A callback for another destination or state must
   not authenticate; a consumed code cannot be exchanged again.
4. Make the access token expire in a test tenant or controlled fixture. Confirm
   refresh succeeds, while an invalid refresh credential requires sign-in again.
5. Sign out while an account request is pending. Its late result must not restore
   the account. Test credential-store failure using a controlled fixture and
   verify the Retry sign-out state.
6. Repeat sign-in and incoming-link returns from a distributed build using the
   actual registered identity. Check the API's authorization for private data.

The maintained tests exercise adapter requests, real JWT signature/claim checks
using local test keys, and account-state races. They do not qualify an Auth0
tenant, OS browser dialog, Keychain/Keystore or provider registration. Use a
configured app for those steps; a successful docs build is separate evidence.
